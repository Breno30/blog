[**Scalable WordPress**](https://github.com/Breno30/scalable-wordpress) takes an
application usually installed on one public server and gives it a
production-shaped AWS architecture. The goal wasn't to reinvent WordPress. It
was to solve the infrastructure problems that appear when one machine is no
longer enough: network isolation, shared state, horizontal scaling, secrets,
and repeatable provisioning.

## The architecture

```text
Internet ──▶ Application Load Balancer ──▶ EC2 Auto Scaling group
                                                    │
                              ┌─────────────────────┼─────────────────────┐
                              ▼                     ▼                     ▼
                         RDS MySQL            EFS uploads          Valkey cache
```

The VPC spans two Availability Zones and has three distinct network tiers:

- **Public subnets** contain the load balancer and NAT gateways.
- **Private application subnets** contain the WordPress instances, EFS mount
  targets, and cache.
- **Isolated database subnets** contain RDS with no route to the internet.

Only the load balancer accepts public traffic. The EC2 instances have no public
IP addresses, and security groups describe the permitted service-to-service
paths: ALB to WordPress, then WordPress to MySQL, EFS, and Valkey.

## Making WordPress horizontal

Adding an Auto Scaling group is easy. Making the application safe to scale is
the real work.

WordPress normally keeps uploaded media on the local filesystem. If two
instances handled requests independently, an image uploaded through one might
not exist on the other. This stack mounts **EFS** for uploads, so every instance
sees the same files. **RDS MySQL** holds the database, and **ElastiCache
Serverless for Valkey** provides a shared object cache.

With state moved out of the instances, the load balancer can send a request to
any healthy target. Auto Scaling tracks average CPU utilization around 60%, and
an unhealthy or replaced EC2 instance can bootstrap itself instead of requiring
manual repair.

## Bootstrapping instead of configuring by hand

The launch template renders a user-data script that installs and configures the
whole application layer:

```text
Amazon Linux 2023
  ├── Nginx + PHP-FPM
  ├── WP-CLI + WordPress
  ├── EFS mount
  ├── RDS connection
  └── Redis-compatible object cache
```

The RDS password is generated by AWS and stored in **Secrets Manager**. At boot,
the instance retrieves that specific secret through a narrowly scoped IAM role.
There is no database password in `terraform.tfvars`, and there are no SSH keys:
administrative access goes through **Systems Manager Session Manager**.

## HTTPS when there is a domain

The same configuration works as a quick demonstration behind the ALB hostname,
or with a real domain. Setting `domain_name` requests an ACM certificate,
prints the DNS validation records, enables an HTTPS listener, and redirects HTTP
to HTTPS after validation.

That conditional path matters for a reusable example: a domain shouldn't be a
prerequisite for testing the infrastructure, but TLS should be part of the
design when one is available.

## The honest trade-offs

This is a scalable foundation, not a claim that every default is fully highly
available. It starts with one EC2 instance and a Single-AZ RDS database to keep
the demonstration smaller. Production availability would mean raising the
minimum application capacity and enabling Multi-AZ for the database.

The two NAT gateways are deliberately one-per-zone, avoiding a cross-zone
dependency for outbound traffic. They also make up the largest fixed part of an
estimated **$130–$150 monthly bill**. A development version could use one NAT
gateway or redesign outbound access around VPC endpoints, accepting different
cost and resilience trade-offs.

> Scaling isn't adding more servers. It's removing the assumptions that only
> one server exists.

The result is still WordPress, but the infrastructure around it is replaceable,
private by default, observable through AWS, and completely described in
Terraform.
